          01 // HOW THE PROJECT WORKS — THE 5G EDGE TELEMETRY PARADOX & CLOSED-LOOP SLA CONTROL
          MEC VM: 172.16.0.5 | Tailscale: 100.73.187.15
        

        

          

            1. The Problem: Open-Loop Bufferbloat
            

              High-precision industrial sensors stream uncompressed 60Hz RAW_FP32 telemetry (681.6 Kbps) over a standard 5G eMBB (5QI-9) slice. When wireless impairments hit—such as a cell tower handover (+28ms), mmWave line-of-sight blockage (+56ms), or cell PRB congestion (150kbit cap)—keep-alive 60Hz packets pile up inside the Linux kernel upf0 queue. Uplink RTT spikes to 45–95 ms, violating the 30.0 ms URLLC SLA.
            

          

          

            2. The Solution: Sub-Second Closed-Loop Auto-QoS
            

              Our FastAPI MEC controller continuously probes the real Linux kernel upf0 (N3 GTP-U) interface and measures live WebSocket RTT. If RTT breaches 30.0 ms for 2 consecutive ticks, the MEC server sends a downlink control frame over /ws/ue instructing the sensor node to switch to URLLC-COMPACT (15Hz INT8_DELTA, 5QI-80). This cuts wireless bandwidth by 93.5% (down to 44.2 Kbps), drains the UPF packet queue, and pulls RTT back to ~18–20 ms (<30ms SLA) while the radio impairment is still active.
            

          

          

            3. Dual-Source Telemetry + Gemini Edge-AI
            

              When a smartphone connects to /phone, it streams live 60Hz hardware accelerometer & gyroscope vectors (ax, ay, az) over WebSockets. When no phone is connected, the server streams live Ubuntu VM hardware telemetry (psutil RAM, kernel load average, thermal zones, and upf0 packet counters). Pressing [g] or [s] feeds the live snapshot into Google's lightweight Gemini models (gemini-3.1-flash-lite) for an instant 3-sentence operator diagnosis.
            

          

        


        

          02 // REAL-WORLD (IRL) DEPLOYMENT SCENARIOS
          Industry 4.0 / Private 5G Applications
        

        

          

            🏭 Scenario A: Smart Factory CNC Spindle & Robotic Arm Interlock
            

              IRL Setup: The smartphone IMU acts as a 60Hz vibration/shear sensor mounted on a high-speed CNC milling spindle or 6-axis robotic arm connected over factory Private 5G (Band n78).

              Why It Matters: Moving overhead cranes cause temporary mmWave Blockage [3]. If bearing chatter spikes vibration above 0.50g, Closed-Loop Auto-QoS guarantees the anomaly packet reaches the MEC PLC interlock in <30.0 ms before the tool shatters.
            

          

          

            🤖 Scenario B: Autonomous Warehouse AMR / AGV Fleet Control
            

              IRL Setup: Autonomous Mobile Robots (AMRs) driving across a warehouse floor, roaming between indoor 5G small cells ([2] gNB Handover Spike) and sharing cell capacity ([4] PRB Congest).

              Why It Matters: Robots stream 60Hz kinematic odometry to the MEC navigation server. Compressing to 15Hz INT8 (5QI-80) during cell handovers prevents packet queue stalls so emergency collision-avoidance braking stays under 30 ms.
            

          

          

            🖥️ Scenario C: 5G Cell-Site MEC Micro-Datacenter Telemetry
            

              IRL Setup: Remote monitoring of a ruggedized Ubuntu MEC server rack (172.16.0.5) deployed at the base of a 5G gNodeB tower alongside a chassis seismic/shock sensor.

              Why It Matters: Operators correlate Linux kernel upf0 N3 tunnel queuing, VM RAM, and CPU core load with physical rack vibration and server thermal zones—plus execute live tc qdisc remediation via the built-in 2:ssh terminal.
